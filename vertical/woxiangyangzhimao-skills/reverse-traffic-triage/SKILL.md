# 逆向流量诊断与参数溯源（reverse-traffic-triage）

## Scope / 授权

本技能仅用于 **已获得明确授权的安全测试、你自己拥有或运营的应用、公开的学习研究目标、或防御性研究**。逆向第三方系统、绕过他人风控、批量爬取受保护数据可能违反法律与服务条款。开工前先确认目标在授权范围内；不确定就停下来问，别替用户假设授权。本技能不提供任何用于规避访问控制、攻击生产系统或窃取数据的具体指导。

---

## 这个技能解决什么

逆向工程最大的时间黑洞，是看到请求里有个 `sign` 就立刻 `Ctrl+Shift+F` 全局搜 `sign`、然后在搜出来的 200 个匹配里随机打断点。结果：断点全打偏、栈跳得满天飞、几个小时白费，最后还在原地。

问题不在工具，在于 **跳过了从「流量」到「代码」的系统性溯源**。`web-reverse-master` 的 Phase 1 只让你捕获请求、记录字段，但没有任何纪律强迫你在动手前先把参数的来源链走通。这正是 `/goal` `/debug` 那种「先想清楚再动手」的纪律——只是逆向版本一直不存在。

本技能就是那条缺失的纪律。它是 `param-encryptor` 『Step 2 Hook 定位』的**上游前提**：你必须先用本技能确认「这个参数在哪一行被算出来」，才有资格进入算法分析。

**何时使用**：已经抓到目标请求（HAR 或 DevTools Network），但还没确认加密/签名参数在哪段 JS 生成时。即——开工逆向任何未知加密参数的**第一步**，在 `param-encryptor` / `ast-deobfuscation` 之前。

---

## 角色规则（铁律）

1. **禁止在完成参数溯源前全局搜参数名或随机设断点。** 全局搜 `sign` 是「感觉在干活」的幻觉，不是溯源。溯源必须从「请求发出的那一刻」沿调用栈往回走，而不是从字符串名字往外猜。
2. **每个加密字段必须标注「证据等级」**，三选一，不许含糊：
   - `已溯源`：已定位到**唯一**入口函数（函数名 + 文件 + 行号 + 一组真实输入输出样本可复现）。
   - `候选`：缩小到了 2–N 个可能位置，但还没排他确认。
   - `纯猜测`：只是看名字觉得像，没有任何调用栈证据。**纯猜测的字段不许进入下游算法分析。**
3. **不准跳步。** 下面五步是有序的，每一步都为下一步缩小搜索空间。跳过分类直接打断点，等于在没有边界的代码海里打捞。

---

## 五步溯源纪律（禁止跳步）

### Step 1 — 字段分类

逐个把请求字段（query / body / header / cookie）标注为三类之一：

- **静态**：值写死在 HTML 源码、JS 常量或 URL 模板里，每次都一样。
- **半静态**：来自 Cookie / localStorage / sessionStorage / IndexedDB，在会话内相对稳定，由某次登录或初始化写入。
- **动态**：每次请求都变。**只有动态字段才需要逆向。**

**手法**：对同一个接口**连抓 2–3 次**，把请求逐字段做 diff。

- 不变的字段 → 静态/半静态，先排除。
- 变化的字段 → 动态，进入下一步。

**为什么重要**：90% 的字段其实是静态或半静态的噪音。先把它们筛掉，你要逆向的目标可能从 30 个字段缩到 1–2 个。

**常见偷懒点**：肉眼扫一眼觉得「这个看起来是随机的」就跳过 diff。肉眼会把递增的时间戳看成「随机」，也会把 Cookie 里搬过来的值误判成「现算的」。**必须用两次抓包的实际 diff 证明动态性，不靠感觉。**

### Step 2 — 动态来源二分

对每个**动态**字段，先回答一个二选一问题：它是「无需逆向的可生成值」还是「需要逆向的加密产物」？

- **无需逆向**：时间戳（13 位毫秒 / 10 位秒）、随机数（`Math.random` / UUID）、自增计数器、毫秒级抖动。这些你能直接构造，不用扣代码。
- **需要逆向**：固定长度的摘要（32 位 hex = MD5，40 位 = SHA1，64 位 = SHA256）、Base64 块、带分隔符的复合签名、明显的密文。

**判断依据**：看**长度、字符集、编码形态**。

- 纯数字且单调递增 → 极可能是时间戳，对比 `Date.now()`。
- 长度固定、`[0-9a-f]` → 哈希家族，长度直接暴露算法。
- `[A-Za-z0-9+/=]` 且 `=` 结尾 → Base64，先解一层看里面是什么。
- 多段用 `.` `_` `|` 拼接 → 复合签名（如 JWT、`时间戳.随机.签名`），拆开逐段分类。

**为什么重要**：把时间戳和随机数误当加密产物，会让你浪费几小时去逆向一个 `Date.now()`。先二分，能再砍掉一批假目标。

**常见偷懒点**：看到一长串就默认「这是加密的」。先解 Base64、先对时间戳，很多「加密参数」会当场现形。

### Step 3 — initiator 链（定位入口的上界）

打开 DevTools Network，点中目标请求，看 **Initiator** 列 / 面板里的调用栈（Request call stack）。这条栈告诉你：**是哪段代码触发了这个请求**。

- 从栈顶往下，找到第一帧落在**业务/应用代码**里的（跳过 axios、fetch polyfill、框架内部帧）。
- 点进去，那段代码就是「发请求」的位置——**加密参数一定在它执行到这里之前就已经准备好了**。

**为什么重要**：initiator 栈直接框定了「入口的上界」——加密计算只可能发生在这条栈之内或更早，不可能在它之后。你的搜索空间从「整个站点的 JS」缩小到「这条栈覆盖的几个函数」。

**常见偷懒点**：嫌 initiator 栈帧名是压缩后的 `n.t.send` 就放弃。压缩名照样能点进 Sources 看上下文；配合 source map（若有）或格式化（`{}` 美化）就能读。

### Step 4 — XHR/Fetch 断点回溯（找到写入点）

知道了上界，现在在「请求即将发出」的那一刻断下来，沿栈往回找参数被**写入**的那一行。

- 优先用 DevTools 的 **XHR/fetch breakpoint**（Sources → XHR/fetch Breakpoints → 填入 URL 关键片段）。命中后请求还没发出，调用栈完整。
- 或在页面最早期 **Hook `XMLHttpRequest.prototype.send` / `XMLHttpRequest.prototype.open` / `window.fetch`**，在 hook 里 `debugger`。
- 断下后，**沿 Call Stack 逐层向上**单步，盯住你的目标参数值：找到它从「不存在」变成「出现在 body/header/url」的那一帧——那就是**写入点**。

**为什么重要**：写入点是参数「成型」的地方，离计算它的函数已经很近了。从这里继续往回，比从字符串名瞎搜精准一个量级。

**常见偷懒点**：在 send 处断下后只看最顶帧就收工。写入点往往在中间几帧，必须沿栈往上逐帧确认参数是哪一层放进去的。

### Step 5 — 锁定唯一入口

从写入点继续回溯：参数被写入前，是哪个函数**计算**出它的？一直走到那个真正做运算的函数。

记录下这四件事（缺一不可）：

1. **入口函数名**（或它在文件中的定位特征）
2. **文件 + 行号**
3. **一组真实的输入 → 输出样本**（喂什么进去、吐什么出来）
4. 该字段的**证据等级**（应为 `已溯源`）

> **CHECKPOINT（硬门槛）**：拿不到**唯一**入口、给不出一组可复现的输入输出样本，就**禁止**进入算法分析。
> - 如果回溯到多个候选位置无法排他 → 标 `候选`，回到 Step 4 用更精确的条件断点（按参数值条件命中）逐一排除，**不要带着 `候选` 往下走**。
> - 如果连写入点都找不到 → 大概率落入下面的失败模式表，按表处理，别开始全局搜名字。

## 溯源失败模式表

当标准五步走不通，对症查表。先用「一线手段」，不行再上「兜底」：

| 症状 | 一线手段 | 兜底 |
| --- | --- | --- |
| 全局搜参数名 200+ 命中，根本定位不了 | 放弃搜名字，改用 Step 3 的 initiator 栈先缩范围 | Step 4 的 XHR/fetch 断点回溯，从请求倒推 |
| 参数在闭包内的 fetch 生成，Sources 里搜不到那段代码 | 在**页面加载前**就 Hook（`fetch` / `XHR.send`），抢在闭包执行前布点 | 用 CDP（Chrome DevTools Protocol）注入脚本，在更早时机插桩 |
| 参数在 Web Worker 里生成，主线程断点全不命中 | Hook `worker.postMessage` / `onmessage`，从消息边界切入 | 直接进 Worker 上下文设断点（DevTools 可选中 Worker 线程调试） |
| setter 被混淆分发（参数经 `defineProperty` / 数组 push / 动态 append 写入） | 在 `Object.defineProperty` / `Array.prototype.push` / `URLSearchParams.append` / `Headers.set` 上设断点 | 在 `Function.prototype.apply` / `call` 上设**条件断点**（按参数名或值过滤），抓住分发那一刻 |

**通用心法**：每一行的逻辑都是同一个——「从我能确定的边界（请求发出 / 消息发送 / 写入 API）往回追」，而不是「从我猜的名字往外搜」。

## 产出：参数溯源表

完成后输出一张**参数溯源表**，每个动态字段一行：

| 字段名 | 类型（时间戳/随机/哈希/签名/密文…） | 入口函数 | 文件:行号 | 输入→输出样本 | 证据等级 |
| --- | --- | --- | --- | --- | --- |
| `sign` | MD5 复合签名 | `getSign(params, ts)` | `app.a1b2.js:4471` | `("uid=10&t=1718...", 1718000000000)` → `"e3b0c44298..."` | 已溯源 |

这张表是交给下游技能的**交接物**。表里还是 `候选` 或 `纯猜测` 的字段，不算溯源完成。

---

## 交接物 / 下游路由

本技能**只负责「从流量到加密函数入口」的定位纪律**，到此为止。拿到溯源表后，按字段性质分流：

- **入口函数是加密/签名算法**（MD5 / AES / RSA / 自定义摘要）→ 交给 **`param-encryptor`**。溯源表的「入口函数 + 输入输出样本」直接成为它 Step 2 Hook 定位的起点，省掉它自己再找入口。
- **入口函数被混淆得读不懂**（控制流平坦化、字符串加密、变量名全是乱码）→ 先交给 **`ast-deobfuscation`** 还原，再回到 `param-encryptor`。
- **生成依赖浏览器环境**（`window` / `navigator` / `canvas` 指纹 / `document` 检测）→ 交给 **`env-patcher`** 补环境，让入口函数能在 Node 里跑起来。
- **目标参数其实来自验证码/行为验证**（滑块、点选、JS challenge）→ 交给 **`captcha-solver`**，不在本技能与 `param-encryptor` 的范畴内。

**一句话**：本技能产出一张「每个动态字段都有证据等级的溯源表」，把「该逆向哪一行」这件事彻底确定下来，再交棒。没有这张表，下游的所有扣代码工作都是在猜。
