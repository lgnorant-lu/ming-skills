# reverse-parity-gate — 逆向交付前的逐字节对齐验收闸门

## Scope / 授权

本技能仅用于 **已获授权的安全测试、你自有的应用、公开的学习研究目标,或正当的防御性研究**。在动手前确认目标在授权范围内。若用途不明确或涉及未授权系统,先停下来与用户确认,不要继续。口径与 `web-reverse-master` 一致。

---

## 这个技能在解决什么

逆向工程师最常见、也最致命的自欺是:**本地算出一个值,长度对了、格式像了,就宣称「签名还原成功」**。但「像」不是「一致」。跳过和浏览器真实输出的逐字节对照,等于把验收外包给了线上服务器——结果就是交付后线上一直 403,回头排查才发现:padding 模式不一样、参数拼接顺序差一个 `&`、Base64 用了 URL-safe 变体、JSON key 顺序不同、末尾多了个 `\n`。

这是 `/verification-before-completion`「无证据不许说完成」那条铁律的**逆向专版**。通用验证技能跑的是构建 / 测试,完全覆盖不了逆向独有的陷阱(编码变体、padding、动态字段归因、隐藏输入)。各 recipe 技能(param-encryptor / env-patcher / captcha-solver)虽然都在结尾写了「必须对照验证」,但那只是一句 CHECKPOINT;本技能把它独立成一道**可触发、可逐项核对、有产出物**的验收纪律。

像 `/goal` `/debug` 那样——**逼你先做对再往下走**。

---

## 铁律

> **无逐字节对照证据,禁止说「还原成功」。本地像 ≠ 一致。**

只要你还没拿出「本地输出 vs 浏览器输出的逐字节 diff,且每个不一致字节都已归因」,你就**不被允许**对用户说出下面任何一句话:

- 「签名对上了」「还原完成了」「可以交付了」
- 「应该没问题了」「逻辑是对的」
- 「本地能跑了,集成进去吧」

长度一致、格式相似、个别样本碰巧通过——**都不算证据**。线上服务器返回 200 也不算充分证据(可能它对这个字段根本没做强校验,或你恰好命中了缓存)。唯一的证据是:**你能逐字节解释本地输出为什么等于(或合理地不等于)浏览器输出。**

---

## 验收四步

每一步都是闸门。**不通过当前步,不许进入下一步,更不许跳到交付。**

### 第 1 步:采样(Sampling)

从真实浏览器(或抓包工具)采集 **≥ 3 组** `(输入 → 输出)` 样本。

- **手法**:在 Chrome DevTools / 抓包工具里固定一个目标接口,记录每次请求的**完整原始输入**(明文参数、URL query、body、相关 cookie / header / 时间戳)和**对应的加密输出**(签名 / sign / token / 加密 body)。原始字节优先——用「Copy as cURL」或保存 raw bytes,不要靠肉眼誊抄。
- **必须覆盖**至少一组**含动态字段**(时间戳 / nonce / 随机 IV)的请求。这是为了让你后面能区分「确定性字节」和「随机字节」——只采一组样本,你根本分不清哪些字节是算法决定的、哪些是每次都变的。
- **为什么重要**:样本是整个验收的地基。样本不全 / 不真 / 没记全输入,后面所有对照都是在错误前提上做的。
- **常见偷懒点**:只抓一组就开始对;输入只记了「看得见的参数」,漏了隐藏的指纹 / 上一次响应里带回来的 token / 默认 header;誊抄时手滑改了一个字符。

> **CHECKPOINT 1**:我是否有 ≥ 3 组真实浏览器样本,其中至少一组含动态字段,且每组的**完整输入**都已记录(包括我一开始没注意到的隐藏输入)?
> 否 → 回去补采,不许往下。

### 第 2 步:字节对齐(Byte Alignment)

把本地输出和浏览器输出做 **hexdump 逐字节 diff**。

- **手法**:`xxd` / `hexdump -C` / Python `binascii.hexlify`,把两边输出都转成十六进制,逐字节对齐比较。文本类输出也要走 hex——肉眼看 Base64 字符串是发现不了「末尾少一个 `=`」「`+` 变成了 `-`」这种差异的。
- **标记**:完全一致的字节段标 `OK`;不一致的字节段进入第 3 步归因,**一个都不能放过**。
- **为什么重要**:hex diff 是唯一能暴露编码变体、padding、不可见字符(`\r` `\n` 空格)的手段。在字符串层面「看起来一样」的两个值,hex 层面可能差好几处。
- **常见偷懒点**:用 `==` 比字符串就当对过了;只比前几个字符 / 只比长度;输出里有随机段就干脆整体跳过对照。

> **CHECKPOINT 2**:我是否对每一组样本都做了完整的 hex 逐字节 diff,并明确标出了所有不一致字节段?
> 否 → 去做 diff,不许往下。

### 第 3 步:动态字段归因(Dynamic Field Attribution)

第 2 步标出的**每一个**不一致字节,都必须归到一个**明确的原因**。

- 允许的归因(且必须能说清楚):
  - **时间戳精度**:ms 还是 s?13 位还是 10 位?这几个字节确实对应时间且差异落在合理时间窗内。
  - **随机 IV / nonce**:给定**相同输入**,这段该不该一致?如果是真随机 IV,不同是正常的;如果你以为是固定 IV 却每次都变,说明你认错了它的性质。
  - **计数器 / 序号**:递增字段,差值合理。
  - **session 密钥 / 协商密钥**:每个会话不同,但同会话内应稳定。
- **铁律**:**无法归因的差异 = 算法没还原对。STOP。** 不许用「可能是随机的吧」「应该不影响」糊弄过去。一个你解释不了的字节,就是一个你还没理解的算法分支。
- **为什么重要**:这一步是「本地像」和「本地对」的分水岭。把所有差异都归因清楚,你才真正理解了算法;归因不清就交付,等于赌线上不校验那几个字节。
- **常见偷懒点**:把所有不一致都甩锅给「随机数」;不验证「时间戳字节」是否真的随时间变化就认定它是时间戳;对一段看不懂的差异选择性失明。

> **CHECKPOINT 3**:每一个不一致字节是否都归到了一个我能说清楚的原因?是否存在**任何一个**我归因不了的字节?
> 存在 → 算法没还原对,STOP,回到 param-encryptor 继续逆,不许说「完成」。

### 第 4 步:隐形陷阱清单逐项核对(Invisible-Trap Checklist)

即使字节大体对上,也要把下面这些**隐形陷阱**逐项打勾。这些是线上 403 的高频元凶,且全都在字符串层面「看不出来」。

- [ ] **Base64 变体**:标准(`+` `/`)还是 URL-safe(`-` `_`)?
- [ ] **padding**:Base64 末尾 `=` 有没有 / 对不对?加密 padding 是 PKCS7 / ZeroPadding / NoPadding?
- [ ] **参数拼接顺序**:键的排序是字典序、插入序,还是固定模板序?分隔符是 `&` 还是别的?有没有差一个分隔符 / 多一个尾随分隔符?
- [ ] **大小写**:hex 输出大写还是小写?header / 参数名大小写敏感吗?
- [ ] **trailing 换行 / 空白**:末尾有没有 `\n` `\r\n` 或空格?
- [ ] **编码 charset**:明文按 UTF-8 还是 GBK 取字节?有中文 / emoji 时尤其致命。
- [ ] **JSON key 顺序 / 序列化风格**:key 顺序、空格(`": "` vs `":"`)、是否转义非 ASCII(`ensure_ascii`)?
- [ ] **数字精度 / 格式**:整数 vs 浮点、科学计数、前导零、布尔大小写。

- **为什么重要**:前三步保证了「核心算法对」,这一步保证「外层封装对」。算法对了但 Base64 用错变体,线上照样 403——而且这种错最难查,因为本地一切看起来都正常。
- **常见偷懒点**:跳过这张表,觉得「字节都对上了还查这个干嘛」;只在脑子里过一遍而不真正逐项打勾。

> **CHECKPOINT 4**:这张清单是否**逐项**核对并打勾(不是默认全过)?有任何一项不确定 → 当作未通过,去核实。

## 给定相同输入的复现性测试(关键卡口)

这是揪出**隐藏输入**的杀手锏,务必单独做。

- **手法**:**冻结所有已知输入**——固定时间戳、固定 IV / nonce、固定计数器,然后让本地和浏览器在**完全相同的输入**下各产一次输出。
  - 浏览器侧冻结:可在 DevTools 里 hook / mock `Date.now`、随机数源,或直接在控制台手动喂固定值给签名函数。
- **判定**:冻结之后,本地与浏览器**必须输出完全相同**(逐字节)。
  - **不同 → 还有你没找到的隐藏输入。** 常见的隐藏输入:浏览器指纹 / canvas / UA、固定盐、上一次响应里带回来的 token、localStorage / cookie 里的某个值、环境相关的常量。
- **为什么重要**:正常对照里,随机字段会掩盖「你漏了一个输入」这件事——因为输出本来就每次不同,你会误以为差异都来自随机。冻结输入后差异无处可藏:还不一致,就一定有黑手。
- **常见偷懒点**:嫌麻烦不冻结,直接拿带随机的输出来回比,然后把「对不上」继续甩锅给随机数,陷入无限循环。

> **CHECKPOINT 5**:冻结全部输入后,本地与浏览器输出是否逐字节相同?
> 否 → 存在未找到的隐藏输入,回 param-encryptor / env-patcher 继续挖,不许说「完成」。

## 隐形差异速查表

对不上时,先用这张表对症定位,别瞎改:

| 现象 | 根因 | 验证动作 |
| --- | --- | --- |
| 长度一致、内容全不同 | Key / IV 错(或认错算法) | 冻结输入,对比加密**中间态**(轮密钥 / 块输出),定位第一处分叉 |
| 长度只差几字节 | padding 模式不同 | 对比明文块数与块大小,核对 PKCS7 / Zero / No padding |
| 偶尔对、偶尔错 | 时间戳 / 随机 IV 在作怪 | 冻结后复测;若冻结后就稳定,确认是动态字段而非算法错 |
| 本地对、线上错 | 拼接顺序 / 编码变体 / 隐形陷阱 | 对照**原始请求体 bytes**(非字符串),逐项过第 4 步清单 |

## 产出:parity 报告

验收的产出物是一份 **parity 报告**(可以是给用户的结构化回复,不必落盘成 md):

1. **每组样本的 diff 结论**:N 组样本,逐组写明「逐字节一致」或「不一致字节段 + 归因」。
2. **每个动态字段的归因**:哪些字节因时间戳 / 随机 IV / nonce / 计数器而不同,各自说清。
3. **复现性测试结果**:冻结输入后是否逐字节相同。
4. **隐形陷阱核对表**:第 4 步那张清单,逐项勾选状态。

**全绿(四步 CHECKPOINT + 复现性测试 + 清单全过)才放行交付。** 任何一项红,回退到对应的 recipe 技能继续,**不许对用户说「完成」**。

报告里同时必须诚实写出:**已验证什么 / 未验证什么及原因**(口径同全局指令)。

## 交接物 / 下游路由

本技能是 **交付前的统一验收闸门**,自身不实现算法。根据验收结果路由:

- **算法层不一致(CHECKPOINT 3 / 5 红)** → 回 **`param-encryptor`** 继续还原加密 / 签名算法,或 **`ast-deobfuscation`** 先把混淆代码还原清楚再逆。
- **复现性测试发现隐藏输入是环境 / 指纹类** → 交 **`env-patcher`** 补环境(canvas / UA / navigator 等),补完再回本闸门复验。
- **被验收的输出是验证码 / 风控 token** → 交 **`captcha-solver`** 处理,产出后同样回本闸门做逐字节验收。
- **四步全绿** → 放行,可把 `signer.py` / `signer.js` 集成进主脚本发真实请求;此时再交由 `web-reverse-master` / 集成测试推进。

> 一句话:**param-encryptor / env-patcher / captcha-solver 负责「做出来」,reverse-parity-gate 负责「证明它真的对」。证不出来,就没做完。**
