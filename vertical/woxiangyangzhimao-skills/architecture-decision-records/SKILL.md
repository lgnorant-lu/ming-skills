# 架构决策记录 (ADR)

把项目里「为什么这么选」的关键决策，实时固化成结构化文档，避免几个月后没人记得当初的取舍。

## 何时触发

- 用户明说「记一下这个决策 / ADR this / 记录一下我们的选择」
- 出现决策信号：「我们决定用 X 不用 Y」「最终选 X」「就用 X 吧」
- 认真对比多个框架 / 库 / 数据库 / 架构方案并得出结论时
- 引入一个会长期影响项目的技术选型、目录结构、协议或约定

**不要**为琐碎、可轻易回退的小选择写 ADR（那是噪音）。只记「改起来代价大、后人会问为什么」的决策。

## 写入前先确认（PROPOSE-FIRST）

落盘前先向用户复述你捕获到的决策四要素（背景 / 选了什么 / 排除了什么 / 理由），用户点头再写。不要把没确认的推断当成已定决策记录。

## ADR 文档格式（Nygard 精简版）

存放位置：`docs/adr/NNNN-短横线标题.md`（NNNN 四位递增序号，如 `0007-use-postgres-over-mongo.md`）。

```markdown
# NNNN. <决策标题>

- 状态: 已接受 | 已废弃 | 被 ADR-XXXX 取代
- 日期: YYYY-MM-DD

## 背景 (Context)
是什么问题 / 约束 / 压力促使我们要做这个决策。只写事实，不写结论。

## 决策 (Decision)
我们决定做什么。一句话说清，主动语态。

## 备选方案 (Alternatives)
认真考虑过的其它选项，以及为什么没选（各一两句）。

## 后果 (Consequences)
带来的好处、代价、以及后续要注意的约束（正反都写）。
```

## 工作流程

1. 识别决策信号 → 捕获 背景 / 选择 / 备选 / 理由 四要素。
2. 向用户复述确认（PROPOSE-FIRST）。
3. 查 `docs/adr/` 现有最大序号，取下一个 NNNN。
4. 按模板写入新文件；若本决策取代了旧 ADR，把旧文件状态改为「被 ADR-NNNN 取代」。
5. 告诉用户写到了哪个文件。

## 目录初始化

若项目还没有 `docs/adr/`，先建目录并写一个 `0001-record-architecture-decisions.md`（记录「我们决定用 ADR 记录架构决策」这件事本身），作为惯例起点。

## 反模式

- 事后补写一堆 ADR 凑数 → ADR 要在决策发生时记，才有价值。
- 把实现细节 / bug 修复写成 ADR → 那是 commit message / 普通 docs 的事。
- 只写「决定用 X」不写「为什么排除 Y」→ 后人最想知道的就是排除理由。
