## §3 目标与边界

### 职责边界(强制,先读)

**skill 只负责逆向加密函数的算法**。被加密的数据(输入参数)由**用户提供**,skill 不负责生成。

**含义(对方案 1/2 判定的根本影响)**:
- "参数依赖浏览器运行时" **不再阻碍方案 1**。无论参数是来自 HAR / trace / 用户操作 / 浏览器环境字段 / 异步环境检测,只要算法本身可静态还原,就走方案 1。用户负责在调用 Python 函数时传入对应数据。
- **真正阻碍方案 1 的只有一类**:算法本身不可静态还原(JSVMP / 重度混淆 / 非标准混淆 / 算法代码路径调用浏览器 API 且无法用 Python 等价替代)。
- 方案 1 的 Python 函数签名 = (用户传入的输入参数) → 加密参数输出。skill 负责把"算法"跑通,不负责"数据从哪里来"。

**用户数据提供方式**(见 5.3.1 Step 2 参数溯源):
- 用户从 HAR 捕获请求/响应参数
- 用户从 trace 捕获环境指纹字段
- 用户用 Python 等价生成(`os.urandom` 替代 `crypto.getRandomValues`、`time.time()` 替代 `Date.now()`)
- 用户手动传入业务参数(滑块偏移/时间戳/会话 token)

## §4 Gotchas

- **Gotcha 1(参数来自浏览器误判方案 2)**:Agent 看到"参数来自浏览器"就误读为"参数生成依赖浏览器",直接跳方案 2 → 先问"算法本身是不是纯计算?" 是 → 方案 1,用户负责传数据;否(算法本身依赖浏览器 API 产出密钥材料)→ 方案 2(见 5.2.4)
- **Gotcha 2(算法代码路径 vs 输入参数生成)**:"算法代码路径调用浏览器 API" ≠ "用浏览器 API 生成输入参数"。前者算子本身依赖浏览器 → 走方案 2;后者只是数据来源,数据可由用户用 Python 等价生成 → 走方案 1(见 5.2.2 关键区分)
- **Gotcha 3(跳过方案 1 必试清单)**:不要一上来就 iv8 整文件跑,必须先走 5.2.1 步骤 1 方案 1 必试清单(见 5.2.3 禁止跳级)
- **Gotcha 4(方案 1 试跑失败硬调试)**:方案 1 试跑对不齐浏览器时,快速检查参数对齐排除笔误后,直接降级方案 2,不要搭建动态调试环境做深入根因分析(见 5.3.3)
- **Gotcha 5(iv8 调试循环不止损)**:iv8 连续 3 次同类错误必须止损,不得继续在 iv8 调试循环中反复尝试(见 5.4.2)
- **Gotcha 6(逻辑可读懂判定时机)**:必须在 2.1 字符串表完全还原 + 2.3 局部去壳(若涉及)完成后判定"逻辑可读懂",2.1 未完成时不得判定(见 5.2.1 步骤 1)
- **Gotcha 7(iv8 debug 大文件日志)**:大文件 debug 日志量过大,必须设置预警阈值(见 [SKILL.md](../../SKILL.md) "iv8 debug 模式预警")
- **Gotcha 8(iv8 接口级桩函数,v9.22 新增)**:iv8 在 V8 引擎之上提供广泛的浏览器 API 模拟层,部分为**接口级桩实现**——重型浏览器 API(WebRTC/WebTransport/Sensors 等)类存在但方法是空桩,调用时**静默 reject 或返回 null**,不会被 JS 层 Promise hook 拦截。**症状**:方案 2 iv8 补环境后加密参数生成失败/Promise 链中断/指纹采集异常,但无报错。**对策**:见 [api-reference.md](../modules/api-reference.md) "社区版桩函数形态与实测清单"(4 种形态 + 6 类已实测清单 + 探测方法),在 page.load 之前用 JS 覆盖 prototype 方法。**最隐蔽的是形态 1(C++ 层 reject)**:绕过 JS 层所有 Promise hook,必须 hook `unhandledrejection` 事件才能捕获
- **Gotcha 9(iv8 内存爆破,v9.23 新增,强制)**:方案 2 iv8 补环境时,目标 JS 代码可能因死循环分配、大数组构建、递归爆栈等导致内存爆破,拖垮主进程。**强制规范**:所有 iv8 使用场景必须设置最大内存限制(默认 512MB)。**3 层策略**:第 1 层(必须)`ctx.close(gc="low_memory")`;第 2 层(推荐,Windows)子进程 + Job Object;第 3 层(高安全)第 2 层 + psutil 监控。**不可信 JS / 大文件(200KB+)必须实施第 2 层**。完整规范与代码模板见 [api-reference.md](../modules/api-reference.md) "内存限制(必读,防内存爆破)"
- **Gotcha 10(参数化自定义误判"魔改"→跳方案 1,v9.29 新增)**:看到"自定义轮函数/自定义块大小/自定义 S 盒/自定义操作序列"不要直接判定为"魔改 → 方案 2"。方案 1 的判定标准只有两条:(1) 逻辑可读懂(2.1+2.3 完成后);(2) 算法代码路径不调用浏览器 API 产出密钥材料。参数化自定义(常量可从代码提取 + 逻辑可重写)不阻碍方案 1。**实战教训**:网易易盾 v3/check 的 AES 变体(自定义轮函数 + ROUND_KEY 控制 7 种操作:XOR/S-BOX 查表/位移),Agent 误判"魔改 → 方案 2",实际方案 1 用 Node.js 手写 200 行即跑通——S-BOX 是标准 AES S-BOX,ROUND_KEY 只是模块内的字符串常量,grep 即可提取
- **Gotcha 11(方案 1 实现策略:提取重写,禁止加载完整 JS + hook,v9.29 新增)**:方案 1 是"理解算法 + 重写算法",不是"加载完整 JS + hook 捕获内部函数"。后者是方案 2 的思路,在方案 1 场景下会因 IIFE 闭包单体(window 未定义/getAttribute is not a function 等)反复失败。**正确做法**:从脱壳代码中理解加密流程 → 提取所有常量(S 盒/密钥/轮密钥/IV)→ 用 Node.js/Python 独立重写算法逻辑。**禁止**:在方案 1 场景下用 iv8/Node.js 加载完整 JS + hook 捕获内部函数

### 5.1 附录:分支实现指引(原 stage4.md §4.2-§4.5 迁移,v9.26)

> 本附录给出分支 A/B/C/D 的具体实现流程。阶段三已确认分支选择(见 [stage3.md](stage3.md) §3.6),本阶段按所选分支执行实现。

#### 5.1.1 分支 A:WASM

4. Python 调用 wasmtime 或 pywasm 运行(不补环境)
   └─ 若胶水逻辑复杂,可提取胶水代码用 iv8 运行(page.load 加载)
```

- **不补环境**(wasm 是独立的运行时,不依赖浏览器环境)
- 胶水层有壳时,先去壳胶水层(阶段二)再提取 WASM
- **不参与方案 1/2 降级链**(分支 A 直接 Python wasmtime 运行,不走 §5.2/§5.3)

#### 5.1.2 分支 B:JSVMP

```
1. 提取解释器代码及字节码
2. 判断文件结构:
   ├─ 文件含业务+JSVMP 混合 → 先扣出 JSVMP 部分(函数/对象),再 iv8 补环境
   └─ 整文件是 JSVMP → 直接 iv8 整文件补环境
3. iv8 本地环境运行(debug 模式定位环境缺口)
4. 补全缺失对象(见 [iv8-env-patching.md](iv8-env-patching.md))

- 静态不可读,扣不了代码
- **必定 iv8 补环境**(分支 B 必走 iv8,不走 §5.2 方案 1)
- **不参与方案 1/2 降级链**(分支 B 直接 iv8 补环境,不走 §5.2/§5.3 的方案选择)

##### JSVMP Recovery Level

JSVMP 标签场景默认从 Level A 起步,只有证据表明当前级别无法支撑下一阶段时才升级。

| 级别 | 适用条件 | 交付物 |
|------|---------|--------|
| A(默认) | 写回边界已明确,少量 opcode 语义就足以解释目标字段 | 关键 opcode 卡片 + I/O 对照 + 形成路径 |
| B(升级) | A 无法解释 → opcode 含义依赖 dispatcher/寄存器/栈/上下文 | dispatcher loop + 关键状态载体 + 带状态流的 opcode 家族 |
| C(升级) | B 无法支撑 → 必须重放多条路径或协议重建 | 最小反编译结果或最小解释器 + 关键路径验证样本 |

**硬性升级规则**:

- 不能因代码脏/平坦化重/字符串表复杂就直接跳 C
- A→B 需满足:关键 opcode 不恢复 dispatcher 语义就无法解释,或目标字段解释依赖寄存器/栈/上下文流
- B→C 需满足:下游要求重放多条执行路径,或协议重建要求最小可执行片段

**IIFE 闭包单体例外(v9.26 新增)**:

当 JSVMP 代码是 IIFE 闭包单体(整文件是一个自执行函数,内部变量/函数均在闭包内,见 [stage3.md](stage3.md) §3.3.1 IIFE 闭包单体判定)时,Recovery Level 概念**基本失效**——因为:
- 整文件作为闭包单体,无法拆分单独提取 JSVMP 解释器部分
- `page.load` 整文件直接运行,无需逐 opcode 恢复
- 闭包内变量对外不可见,只能通过源码注入 hook(见 [code-extraction.md](code-extraction.md) §5.5)

**IIFE 闭包单体场景的处理流程**(替代 Recovery Level):

```
IF JSVMP 代码是 IIFE 闭包单体(见 stage3.md §3.3.1 判定)
   THEN 跳过 Recovery Level 判定,直接执行:
      1. page.load 整文件加载(不拆分)
      2. iv8 debug 模式定位环境缺口
      3. 补全缺失对象(见 [iv8-env-patching.md](iv8-env-patching.md))
      4. 用源码注入 hook 提取闭包内加密函数(若需)
      5. §5.5 验证
   → 在 stage5-verify.md §1 标注"IIFE 闭包单体,跳过 Recovery Level"
```

#### 5.1.3 分支 C:标准 JS 加密(含 Webpack + 无附加保护)

## 5.2 方案 1/2 选择判定(分支 C 专用)

分支 C(标准 JS 加密,含 Webpack + 无附加保护)在阶段四做方案 1/2 选择判定。**本节负责判定走方案 1 还是方案 2**。

**判定核心原则**(见"职责边界"):只看"算法本身能否静态还原",**不看**"参数是否依赖浏览器"。被加密数据由用户提供,不阻碍方案 1。

### 5.2.1 方案选择状态机(If/Then,强制)

```
IF 载体形态判定为分支 C
   THEN 进入方案选择状态机(必须按以下顺序判定,不得跳级)

步骤 1:方案 1 必试清单(满足以下全部条件 → 必须先尝试方案 1)
   ├─ 逻辑可读懂(2.1 字符串表完全还原 + 2.3 局部去壳完成后能理解加密流程)
   └─ 算法代码路径不调用浏览器 API 产出密钥材料
   IF 全部满足 → 必须走方案 1(Python 重写,实现见 §5.3)
   IF 任一不满足 → 进入步骤 2

   > **"逻辑可读懂"判定时机(强制)**:必须在 2.1 字符串表完全还原 + 2.3 局部去壳(若涉及)完成后判定。2.1 未完成(字符串表未完全还原)时**不得**判定"逻辑不可读"——此时不可读是字符串未还原导致的,不是逻辑本身不可读。判定流程:
   > 1. 2.1 完成 → 检查是否需要 2.3(命中其他壳特征)
   > 2. 2.3 完成(或无需 2.3)→ 此时判定"逻辑可读懂"还是"逻辑不可读"
   > 3. 逻辑可读懂 + 不调用浏览器 API → 方案 1;否则 → 方案 2

   > **参数依赖浏览器不阻碍方案 1**(v9.17 重构,见"职责边界"):不要再判定"参数生成逻辑是否依赖浏览器运行时"——这不再是方案 1 的阻碍条件。无论参数来自 HAR/trace/用户操作/浏览器环境字段/异步环境检测,都由用户在调用 Python 函数时传入。方案 1 只关心算法本身能否静态还原。

   > **参数化自定义不阻碍方案 1**(v9.29 新增,见 §4 Gotcha 10):看到"自定义轮函数/自定义块大小/自定义 S 盒/自定义操作序列"不要直接判定为"魔改 → 方案 2"。只要常量可从代码提取 + 逻辑可重写,就不阻碍方案 1。

步骤 2:方案 2 触发条件(满足任一 → 直接方案 2,可跳过方案 1)
   ├─ 2.1 + 2.3 完成后逻辑仍不可读(JSVMP / 重度混淆 / 非标准混淆)
   ├─ 算法代码路径调用浏览器 API 且无法用 Python 等价替代(见 §5.2.2)
   └─ 方案 1 已试跑失败(见 §5.3.3 试跑失败处理)

步骤 3:方案 1 试跑失败 → 降级方案 2(见 §5.3.3)
   方案 1 试跑输出对不齐浏览器 → 快速检查参数对齐(排除笔误)→ 非笔误直接降级方案 2
```

### 5.2.2 方案 1 判定条件

**触发条件**:见 §5.2.1 步骤 1(方案 1 必试清单全部满足)。

**算法代码路径是否调用浏览器 API 判定**:

```
IF 算法代码路径只做纯计算(位运算/算术/查表/编码)
   AND 不调用浏览器 API(window/document/navigator/DOM/网络/存储等)产出密钥材料
   → 不阻碍方案 1
   → 输入参数由用户提供(见 §5.3.1 Step 2 参数溯源)

IF 算法代码路径调用浏览器 API 且无法用 Python 等价替代
   (如:加密过程中实时读取 DOM 尺寸/调用 WebGL/canvas 渲染产出密钥材料)
   → 阻碍方案 1 → 走方案 2

IF 代码看起来调用浏览器 API,但只是用来生成"输入参数"(如 crypto.getRandomValues 生成 IV)
   → 输入参数可由用户用 Python 等价生成(os.urandom)→ 不算"算法代码路径调用浏览器 API"
   → 算法本身仍是纯计算 → 不阻碍方案 1
```

> ⚠️ **关键区分**:"算法代码路径调用浏览器 API" ≠ "用浏览器 API 生成输入参数"。前者算子本身依赖浏览器 → 走方案 2;后者只是数据来源,数据可由用户用 Python 等价生成 → 走方案 1。详见 §5.2.4 Gotcha。

### 5.2.3 方案 2 触发条件

**触发条件**:见 §5.2.1 步骤 2(方案 2 触发条件任一满足)。

满足以下任一条件 → 直接走方案 2(iv8 补环境,实现见 §5.4):

- 算法是 JSVMP / 重度混淆 / 非标准混淆(2.1 + 2.3 完成后仍静态不可读)
- "逻辑可读懂"不满足(2.1 + 2.3 完成后仍不可读)
- 算法代码路径调用浏览器 API 且无法用 Python 等价替代(§5.2.2 判定不满足)
- 方案 1 已试跑失败(见 §5.3.3)

> **与分支 B 区分**:方案 2 是分支 C 的兜底,分支 B 是 JSVMP 必走 iv8。动机不同,但实现都是 iv8 补环境。

> **禁止跳级**:不要一上来就 iv8 整文件跑。必须先走 §5.2.1 步骤 1(方案 1 必试清单),只有清单不满足或试跑失败才能走方案 2。违反此规则 = 违反 [SKILL.md](../../SKILL.md) "阶段门阻断规则"。

### 5.2.4 ⚠️ 方案 1 判定 Gotcha(历史教训,必读)

> **历史教训(极验4 w 参数误判案例,v9.14-v9.16 版本)**:
>
> 实战中 Agent 看到 w 参数的输入数据(滑块偏移/时间戳/环境指纹)来自浏览器,就误读"参数含浏览器环境动态产生"为"参数生成依赖浏览器",直接跳方案 2(iv8 补环境)。但 w 的加密算法(RSA+AES)是纯计算,输入数据都可从 HAR 捕获后传给 Python,方案 1 完全可行。Agent 绕了一大圈搞 iv8,因 Python 沙箱问题跑不通,又回到方案 1,浪费大量时间。
>
> **v9.14-v9.16 的修复(已被 v9.17 替代)**:把"数据来自浏览器"和"参数生成依赖浏览器运行时"区分为两类,前者不阻碍方案 1,后者阻碍方案 1。
>
> **v9.17 的根本修复(本版本)**:彻底删除"参数生成依赖浏览器运行时"这一判定维度。理由:skill 只负责逆向算法,**被加密数据由用户提供**。"参数依赖浏览器"根本不是方案 1 的阻碍条件——只要算法本身可静态还原(纯计算 + 不调用浏览器 API 产出密钥材料),就走方案 1,用户负责在调用时传入对应数据(从 HAR/trace 捕获,或用 Python 等价生成如 `os.urandom` 替代 `crypto.getRandomValues`)。
>
> **唯一仍阻碍方案 1 的情形**:算法代码路径本身调用浏览器 API 且无法用 Python 等价替代(如加密过程中实时读取 DOM 尺寸作为密钥材料)。这种情况下连"算法"都跑不通,必须走方案 2。
>
> **通用启示**:看到"参数来自浏览器"时,先问"算法本身是不是纯计算?" 是 → 方案 1,用户负责传数据;否(算法本身依赖浏览器 API 产出密钥材料)→ 方案 2。

### 5.3.1 重写流程

```
Step 1: 提取加密算法逻辑
   → 从脱壳后代码中理解加密流程(读代码,不是运行代码)
   → 提取所有常量(S 盒/密钥/轮密钥/IV 等)

Step 2: 参数溯源(强制,见"职责边界")
   → 列出算法所有输入参数,逐一标注来源类型:
      ├─ HAR 接口返回(参数 X 来自 /api/getA 响应)
      ├─ trace 字段(参数 Y 在 trace 中作为 navigator.userAgent 被读取)
      ├─ 用户操作(参数 Z 来自滑块轨迹,记录在 HAR 请求 body)
      ├─ 固定常量(参数 W 是硬编码值)
      ├─ 浏览器 API 生成(参数 V 通过 crypto.getRandomValues 生成 → 用户用 os.urandom 等价)

Step 3: Python 实现
   → 算法本身无依赖,纯计算
   → 所有输入参数作为函数参数,用户传入
   → 产出:Python 函数 + API 说明(含参数来源注释,见 Step 2 溯源表)

Step 4: 试跑验证(见 §5.5)
   → 试跑时用户按溯源表准备输入参数
   → 用 HAR 真实值作为期望输出比对
```

### 5.3.3 试跑失败处理(If/Then,强制,v9.4 重构三步排查)

> **v9.4 重构**:排查顺序固化为"数据→算法→环境"三步,禁止跳步。来源:实战中 Agent 试跑失败后凭感觉跳步排查,常遗漏入参缺失(数据层)或误判为算法错误(实际是发包环境被检测),浪费轮次。

```
IF 方案 1 试跑输出对不齐浏览器(或服务端校验不通过)
   THEN 按以下三步顺序排查(禁止跳步):

   Step 1: 数据齐全性排查(被加密数据是否齐全)
      ├─ 逐参数比对方案 1 输入 vs HAR 真实值
      ├─ 检查入参个数是否完整(对照 stage2-output.md §4.3 入参个数完整性判定)
      ├─ 检查入参来源是否正确(HAR 直接 / 前序接口 / 浏览器环境 / 用户操作 / 动态生成)
      IF 入参缺失或来源错误 → 补齐后重新试跑
      IF 入参齐全 → Step 2

   Step 2: 算法实现排查(算法是否正确)
      ├─ 检查常量是否提取正确(S 盒/密钥/轮密钥/IV 等)
      ├─ 检查编码是否正确(Base64/Hex/URL 编码)
      ├─ 检查运算顺序是否正确(轮函数/位移/异或)
      ├─ 逐项核对"算法对齐检查清单"(见 §5.3.3.1)
      IF 是笔误(变量名/常量/编码) → 修正后重新试跑
      IF 清单 7 项全通过但仍失败 → 怀疑环境问题,进入 Step 3
      IF 非笔误(算法逻辑正确) → Step 3

   Step 3: 环境排查(发包环境是否被检测)
      ├─ 检查 httpx 发包的 UA/Referer/Cookie 是否与 HAR 一致
      ├─ 检查 TLS 指纹是否被检测(改用 curl_cffi impersonate="chrome")
      ├─ 检查请求头顺序是否与真实浏览器一致
      IF 环境对齐后仍不通过 → 降级方案 2

   IF 三步排查均无问题但仍不通过
      THEN 降级方案 2(iv8 补环境)
      ├─ 在 stage5-verify.md §降级原因 记录(三步排查过程 + 哪步发现问题)
      ├─ 进入方案 2(iv8 补环境)流程,见 §5.4
      └─ 禁止:搭建动态调试环境做深入根因分析(违反 [SKILL.md](../../SKILL.md) "禁止事项")
```

#### 5.3.3.1 算法对齐检查清单(v9.6 新增,方案 1 试跑失败 Step 2 必查)

> **规则来源**:GeeTest v4(userresponse 线性变换系数错)+ 网易易盾 ds-4p(7 处算法差异)实战反馈。Agent 在 Step 2"算法实现排查"时凭经验跳查,常遗漏精度/字节序等隐蔽差异,浪费轮次。本清单把"算法对齐"固化为 7 项确定性检查,禁止跳项。
>
> **通用方法论**:本清单适用于所有加密参数逆向(不限于滑块/captcha)。skill 是通用逆向方法论,不为每个业务领域建专项模块。

| # | 检查项 | 常见差异 | 验证方法 |
|---|--------|---------|---------|
| 1 | 采样公式 | 线性变换系数错(如 `0.9940884871298692*setLeft+2.0`) | grep JS 系数,Python 用 Decimal 高精度对比 |
| 2 | 时间语义 | ms vs s / 13 位 vs 10 位时间戳 | 确认 `Date.now()` vs `getTime()/1000` vs `Math.floor(t/1000)` |
| 3 | 坐标语义 | 像素 vs 归一化 / 原点左上 vs 左下 | 确认 JS 坐标系定义(如 `e.offsetX` vs `e.clientX`) |
| 4 | 编码字母表 | Base64 标准表 vs 自定义表 | 提取 JS 字母表常量逐字符对比 |
| 5 | 去重维度 | Set vs Sort+unique / 去重 key | 确认 JS 去重逻辑(如 `Array.from(new Set(arr))` vs `arr.sort().filter`) |
| 6 | 数值精度 | float32 vs float64 / 整数除法 vs 浮点除法 | Python 用 numpy dtype 对齐(如 `np.float32` vs `np.float64`) |
| 7 | 有符号字节 | uint8 vs int8 / 字节序大小端 | 确认 `Uint8Array` vs `Int8Array` / `DataView.getInt8` vs `getUint8` |

**执行规则**:
```
IF 进入 Step 2 算法实现排查
   THEN 必须逐项核对 7 项检查清单(禁止跳项)
   IF 发现差异 → 修正后重新试跑
   IF 7 项全通过但仍失败 → 怀疑环境问题,进入 Step 3
```

**滑块/captcha 场景示例**(内嵌,不建专项模块):
- userresponse 公式 `a*x+b`(a≈0.994, b≈2.0)→ 检查项 1(采样公式)
- offset 标定(真实距离 - 识别距离)→ 检查项 3(坐标语义)
- 缺口图 Base64 自定义字母表 → 检查项 4(编码字母表)
- 轨迹点去重(时间戳 + 坐标)→ 检查项 5(去重维度)

**禁止**:
- ⛔ 凭经验跳查(必须逐项核对 7 项)
- ⛔ 只查常量不查精度(检查项 6/7 是隐蔽差异高发区)
- ⛔ 用 Python 默认 float64 直接对比 JS float32(精度差异导致输出不一致)

### 5.4.0 iv8 调试前置门(v9.30 新增,v9.4 边界明确,强制)

> 规则来源:实战中 Agent 收到"分析加密参数"任务后,跳过"读源码定位加密点"直接进入"环境参数对比",列一堆 navigator/screen/canvas 字段(明文组成部分),浪费轮次且抓不住核心。本规则把"算法确认 → 明文对比 → 环境检测"固化为强制状态机,禁止凭经验跳步。
>
> **v9.4 边界明确**:本前置门的边界是"算法确认 → 明文对比 → 环境检测"三步状态机,在 §5.4.4 动态 JS 处理之后执行。执行顺序:**§5.4.4(JS 来源检查)→ §5.4.0(算法确认 → 明文对比 → 环境检测)→ §5.4.1(补环境流程)**。§5.4.4 解决"JS 文件是否正确",§5.4.0 解决"算法是否正确 + 明文是否对齐",两者职责不同,不可混淆。

**进入 §5.4.1 补环境流程前,必须按顺序通过 3 步前置检查(顺序不可调):**

```
Step 1 (算法确认,强制):
   IF 脱壳后代码可静态分析
      THEN grep 搜索已知加密算法常量:
         - TEA/XTEA delta: 2654435769 / 0x9E3779B9
         - AES S-box: 0x63 / 99 (起始字节) + S-box 表特征
         - MD5 K 值表: 0xd76aa478 等 64 个常量
         - SM4 FK: [0xa3b1bac6, 0x56aa3350, 0x677d9197, 0xb27022dc]
         - SM4 CK: 32 个常量(0x00070e15 起始)
         - SHA-256 K 值表: 0x428a2f98 等 64 个常量
         - RSA: 大素数常量 / BigInt 运算特征
      → 命中 → 记录算法类型到 stage5-verify.md §1,进入 Step 2
      → 未命中且脱壳代码可读 → 在 stage5-verify.md §5.3 记录"未识别算法常量"
         → 禁止猜测算法类型
         → 直接进入 Step 2(用 hook 对比明文兜底)
   IF 脱壳后代码不可静态分析(JSVMP / 重度混淆 / IIFE 闭包单体)
      THEN 跳过 Step 1,直接进入 Step 2(iv8 page.load 整文件,用 hook 对比明文)

Step 2 (加密前明文对比,强制):
   hook 加密前入口(对照 stage2-output.md §4.1 入口函数)
   → dump 浏览器侧明文 vs iv8 侧明文
   → 明文一致 → 算法无误,进入 Step 3(环境检测)
   → 明文不一致 → 禁止进入环境检测
      → 回 Step 1 重新确认算法(可能算法识别错误 / 脱壳遗漏函数)
      → 在 stage5-verify.md §5.3 记录"明文不一致,回溯算法确认"

Step 3 (环境检测,仅当 Step 2 明文一致密文不同):
   按 §5.4.1 补环境流程执行
   → 对比 navigator/screen/canvas 等环境字段(对照 stage2-output.md §4.2 环境依赖清单)
   → 按 §5.4.2 指纹值对齐规则补齐

IF 跳过 Step 1/2 直接进入环境检测
   → P0 违规,产物无效
   → 必须回退执行 Step 1/2
```

**禁止事项**:
- ⛔ 禁止跳过 Step 1/2 直接进入环境参数对比(列 navigator/screen/canvas 字段)
- ⛔ 禁止在 Step 1 未命中算法常量时猜测算法类型
- ⛔ 禁止在 Step 2 明文不一致时进入 Step 3 环境检测
- ⛔ 禁止跳过 §5.4.4 动态 JS 检查直接进入本前置门(v9.4 新增,动态 JS 未解决,算法确认无意义)

> 实战教训:网易易盾 collect 参数,Agent 跳过算法确认直接对比环境,5 个诊断脚本均无效;用户纠正后读源码,5 分钟找到 TEA delta 常量 2654435769,确认算法。

### 5.4.2 指纹值对齐与占位规则(v9.31 新增,强制)

> 规则来源:实战中遇到 ft 指纹(如 dy-ele.js 模块 68 `n["default"]()` 计算的哈希)未还原却用占位值交付,skill 无明文规则,Agent 凭感觉判定。本规则消除该歧义。

```
IF 指纹值(ft/userAgent hash/canvas 指纹等)进入加密算法输入
   THEN 必须用 HAR 真实值或等价计算还原,禁止占位
   → 占位会导致加密输出错误,属硬性要求

IF 指纹值不进入加密算法输入(仅作为反检测采集/上报字段)
   THEN 允许占位,但必须同时满足全部条件:
      1. 在 stage5-verify.md §6.2 参数溯源表标注"占位"
      2. 占位理由写明(如"指纹不进入 collect 计算,仅作为 TDC 上报字段")
      3. 同任务有至少 1 个确定性参数严格对齐(=== 比对通过)作为佐证
         → 佐证缺失 → 禁止占位,必须还原指纹

IF 不确定指纹是否进入加密算法输入
   THEN 按"进入"处理(禁止占位)
   → 不确定性归入更严格分支
```

### 5.4.3 iv8 验证失败排查与止损规则(强制,v9.4 重构)

> **v9.4 重构**:新增"验证失败排查顺序"三步(数据→cookie/localStorage→指纹/UA),与原"失败止损规则"合并。来源:实战中 Agent iv8 验证失败后凭感觉排查,常遗漏入口函数被加密数据对齐(数据层)或误判为指纹问题(实际是 cookie 缺失)。

#### 5.4.3.1 验证失败排查顺序(三步,强制)

```
IF iv8 补环境后加密参数输出对不齐浏览器(或服务端校验不通过)
   THEN 按以下三步顺序排查(禁止跳步):

   Step 1: 数据对齐排查(入口函数被加密数据是否对齐)
      ├─ hook 入口函数,dump 浏览器侧明文 vs iv8 侧明文(对照 §5.4.0 Step 2)
      ├─ 检查入口函数入参个数是否完整(对照 stage2-output.md §4.3 入参个数完整性判定)
      ├─ 检查入参来源是否正确(HAR 直接 / 前序接口 / 浏览器环境 / 用户操作)
      IF 入参缺失或不对齐 → 补齐后重新验证
      IF 入参对齐 → Step 2

   Step 2: cookie/localStorage 等网页专属环境排查
      ├─ 检查 cookie 是否注入(page.load headers Set-Cookie / ctx.eval document.cookie)
      ├─ 检查 localStorage/sessionStorage 是否注入(ctx.eval setItem)
      ├─ 检查接口返回值是否注入(add_resource)
      ├─ 检查事件循环是否推进(eventLoop.drain)
      IF 网页专属环境缺失 → 补齐后重新验证
      IF 网页专属环境齐全 → Step 3

   Step 3: 指纹/UA 排查
      ├─ 检查 navigator.userAgent 是否与 HAR 真实值对齐(environment 参数)
      ├─ 检查 location.href / document.referrer 是否对齐
      ├─ 检查 screen / canvas / WebGL 指纹是否对齐(对照 stage2-output.md §4.2 环境依赖清单)
      ├─ 检查 wrapNative 是否伪装补丁(防止 toString 检测)
      IF 指纹对齐后仍不通过 → 进入失败止损规则(§5.4.3.2)

   IF 三步排查均无问题但仍不通过
      → 进入失败止损规则(下文)
      → 在 stage5-verify.md §降级原因 记录(三步排查过程 + 哪步发现问题)
```

#### 5.4.3.2 失败止损规则(原 §5.4.3,保留)

```
IF iv8 连续 3 次同类错误
   → 停止调试,回溯阶段二检查脱壳代码完整性
   → 在 stage5-verify.md §降级原因 记录错误类型 + 止损过程
   → 不得继续在 iv8 调试循环中反复尝试

IF iv8 调试循环超过 5 轮仍未跑通
   → 触发阶段门阻断
   → 检查:
      1. 阶段二脱壳代码是否漏函数(去壳跳过了关键函数)
      2. 阶段三载体形态判定是否准确(是否漏判 WASM/JSVMP/Worker)
      3. 补环境对象清单是否完整(trace stats 是否漏抓 API)

IF 上述检查均无问题,iv8 仍无法跑通
   → 走"任务失败交付物"流程(Black-box reuse 模式已禁用,见 [SKILL.md](../../SKILL.md) P0 禁令)
```

### 5.4.4 动态生成 JS 识别与处理(v9.4 重构,与阶段二 §2.0 衔接,P0 强制,跨方案前置)

> **v9.4 重构**:与阶段二 [stage2-tracing.md](stage2-tracing.md) §2.0 "动态 JS 判定"衔接。阶段二基于 HAR 证据被动判定"是否动态"(预警),本节用 HAR 参数验证"是否干预加密参数生成"(确认),并新增动态文件方案 1 处理路径(httpx 下载 + re 匹配 + Python 本地模拟)。
>
> 规则来源:实战中网易易盾 tdc.js 按 session 动态生成(变量名/内嵌密钥/文件大小每次不同),Agent 用本地缓存的旧文件跑 iv8,导致 collect 环境数据完全错位,卡 2 天靠偶然对比文件 hash 才发现根因。同类场景:极验 gcaptcha4.js、腾讯前端风控 JS。

**适用范围**:进入 §5.3(方案 1)或 §5.4(方案 2)前必须执行(跨方案,方案 1 下载 JS 分析算法、方案 2 page.load 加载 JS 均受影响)。

**与阶段二 §2.0 的衔接(If/Then):**

```
Step 1: 读取阶段二动态 JS 判定结论(来自 stage2-output.md §0)
   → 阶段二已基于 HAR 证据判定:非动态 / URL 动态 / 内容动态 / 未知

Step 2: 干预性验证(确认动态 JS 是否干预加密参数生成)
   IF 阶段二判定 = 非动态
      → 允许使用本地缓存文件
      → 在 stage5-verify.md §5.3 记录"静态 JS,hash: <md5>"
      → 跳过后续步骤

   IF 阶段二判定 = URL 动态 OR 内容动态 OR 未知
      → 必须验证是否干预加密参数生成
      → 干预判定标准(任一命中即判定干预):
         1. 用 HAR 真实参数跑本地缓存的旧 JS,加密输出 P1
         2. 用 httpx 当次请求下载新 JS(带 session cookie),用相同 HAR 参数跑新 JS,加密输出 P2
         3. IF P2 != P1 → 判定干预(动态 JS 影响加密参数生成)
         4. IF P2 == P1 → 判定不干预(动态 JS 不影响加密参数生成,可用本地缓存)
      → 在 stage5-verify.md §5.3 记录:
         - JS URL
         - HAR hash 对比(阶段二 §2.0 证据)
         - P1 vs P2 对比结果(干预性验证)

Step 3: 处理(若判定为干预加密参数生成的动态 JS)
   IF 判定为干预(Step 2 P2 != P1)
      THEN 禁止使用本地缓存的旧文件,必须当次请求 → 当次使用:

      方案 1 路径(Python 重写,优先,v9.4 新增):
         1. Python httpx/curl_cffi 发请求下载 JS(带当次 session cookie)
         2. 若 JS 依赖前置接口(如 prehandle)→ 先调前置接口拿 cookie/path → 再下载 JS
         3. 用 re 匹配提取动态参数(如 AES 密钥/IV/盐值等):
            - 示例:aes_key = re.search(r'var\s+key\s*=\s*["\']([a-f0-9]+)["\']', js_content).group(1)
            - 示例:iv = re.search(r'iv:\s*["\']([a-f0-9]+)["\']', js_content).group(1)
         4. 提取的动态参数作为 Python 函数入参,本地模拟加密算法
         5. 整个流程在单次 Python 调用内完成(不可跨调用复用下载的 JS)
         → 优势:省去 iv8 补环境复杂化,直接用 Python 模拟

      方案 2 路径(iv8 补环境,方案 1 不可行时):
         1. Python httpx/curl_cffi 发请求下载 JS(带当次 session cookie)
         2. 若 JS 依赖前置接口(如 prehandle)→ 先调前置接口拿 cookie/path → 再下载 JS
         3. 下载的 JS 内容直接传入方案 2 的 page.load resources(不落盘或落盘但标记一次性)
         4. 整个流程在单次 Context 内完成(不可跨 Context 复用下载的 JS)

      → 在 stage5-verify.md §5.3 记录:
         - JS URL
         - 两次请求 hash 对比(证明动态生成)
         - 当次下载流程(前置接口 → cookie → 下载)
         - 选择方案 1 或方案 2 的依据(方案 1 优先,若动态参数可 re 匹配提取)

IF 跳过 Step 1/2 直接用本地缓存文件
   → P0 违规,产物无效
   → 加密输出必然错位(变量名/密钥不匹配),无法通过对齐修复

IF 判定为不干预(Step 2 P2 == P1)
   → 允许使用本地缓存文件
   → 仍需在 stage5-verify.md §5.3 记录"动态 JS 但不干预加密参数生成,P1==P2"
```

> **与 §5.4.0 前置门的关系**:§5.4.0 是"算法确认 → 明文对比 → 环境检测"的状态机;本节是"JS 来源检查",在 §5.4.0 之前执行(动态 JS 未解决,算法确认无意义——变量名都变了,grep 常量命中位置也不同)。
>
> **与阶段二 §2.0 的关系**:阶段二基于 HAR 证据被动判定"是否动态"(不发请求,预警用);本节用 HAR 参数 + 当次请求验证"是否干预加密参数生成"(确认用,见 Step 2 干预判定标准)。

### 5.4.5 参与加密生成的上下文项对齐(v9.6 新增,与 §5.4.4 平行,P0 强制)

> **规则来源**:网易易盾 WorkBuddy 实战反馈 — `localStorage.token` 参与加密参数生成,Agent 用 HAR 旧值占位,服务端校验失败。token 本身是加密参数,HAR 旧值会过期,必须逆向其生成机制。
>
> **核心原则**:参与加密生成的上下文项 = 加密参数,必须对齐。两类上下文(见 [stage2-tracing.md](stage2-tracing.md) §2.4.2)对齐策略不同。

**判定流程**:

```
Step 1: 从阶段二 §2.4 取上下文分类清单(网站运行时 / 客户端环境)
   → 读取 stage2-output.md §4.2(网站运行时上下文)+ §4.3(客户端环境上下文)
   → 筛选"是否参与加密生成 = ✅"的项

Step 2: 对"参与加密生成"的项,按类别执行对齐:

   IF 网站运行时上下文 AND 参与加密生成
      THEN 必须逆向生成机制(禁止 HAR 旧值占位,会过期):

      生成机制判定(从 stage2-output.md §4.2 取):
      - HAR 直取(静态值,不过期)→ 直接用 HAR 值
      - 服务端接口下发 → 逆向接口调用流程,本地 httpx 获取新值
        (示例:先调 /api/login 拿 token,再调 /api/encrypt 用 token 加密)
      - 前端动态生成 → 逆向生成算法,本地实现
        (示例:token = md5(timestamp + device_id))
      - 动态生成(session-bound) → 当次请求获取
        (与 §5.4.4 动态 JS 当次下载平行,每次调用都获取新值)

      对齐方式:
      - 方案 1(Python 重写):逆向生成机制,本地生成新值作为 Python 函数入参
      - 方案 2(iv8 补环境):逆向生成机制,本地生成新值后注入 iv8
        (ctx.eval 注入 localStorage / add_resource 注入接口返回值)

   IF 客户端环境上下文 AND 参与加密生成
      THEN 根据服务端校验情况合理设置(保持 iv8 内部一致性):

      服务端校验判定:
      - 服务端不校验具体值(只校验加密参数正确性)
        → 保持 iv8 默认值(方案 2 iv8 内部生成加密参数,读取 iv8 默认值,自洽)
      - 服务端校验具体值(如要求 UA 必须是 Chrome)
        → 用 environment 参数整体覆盖(保持内部一致性)
        → 禁止在 JS 里手动改单个字段

      对齐方式:
      - 方案 1(Python 重写):不涉及 iv8,直接用 HAR 真实值作为 Python 函数入参
        (服务端校验的是请求头/加密参数,Python 发请求时用 HAR 真实 UA)
      - 方案 2(iv8 补环境):见上方"服务端校验判定"

Step 3: 验证对齐
   → 本地生成新值后,注入 iv8 或方案 1 入参
   → 跑加密流程,验证加密参数与 HAR 真实值对齐
   → 若不对齐,检查生成机制逆向是否正确(回到 Step 2)
```

**禁止**:
- ⛔ 网站运行时上下文用 HAR 旧值占位(会过期,导致服务端校验失败)
- ⛔ 客户端环境上下文无脑注入 HAR 采集值(破坏 iv8 内部一致性)
- ⛔ 用 null/undefined 占位(走错误分支)
- ⛔ 只逆向加密参数本身,不逆向其依赖的上下文项(上下文项 = 加密参数)

**与 §5.4.4 的关系**:
- §5.4.4 动态 JS:JS 文件动态生成 → 当次下载
- §5.4.5 动态上下文:上下文项动态生成 → 当次获取/生成
- 两者平行,都是"动态的必须当次处理"

### 5.5.0 目标接口语义分类(必填,验证前先判定)

> 规则来源:不同语义类型的目标接口,"业务正确响应"的判定标准不同。skill 原假设目标是 stateless login,未覆盖 captcha/async 场景。

进入验证前,先判定目标接口属于哪类(填入 stage5.json `validation.interface_type`):

```
IF 目标接口返回 success/token/ticket 等业务成功字段
   THEN interface_type = "stateless-login"
   → 典型:登录、签名校验、token 签发
   → "业务正确响应"判定:业务字段指示成功(code=0 / success=true / ticket 非空)

IF 目标接口的输入参数含会话绑定(sess/ans/ticket 等),会话过期必然返回业务错误码
   THEN interface_type = "session-bound-captcha"
   → 典型:验证码 verify、滑动验证、防水墙
   → "业务正确响应"判定(全部满足才判通过):
      1. HTTP 200
      2. 服务端返回新 sess 或处理凭证(证明请求格式被接受)
      3. 错误码非"格式错误类"(如非 "11"/"12" 参数缺失 / "format_error")
      → 业务码指示会话过期(如 "20" captcha expired/invalid)是预期,不判失败
      → 禁止用"ticket 非空"判定(此类目标天然无 ticket)

IF 目标接口返回 task_id/queue_id 等异步凭证
   THEN interface_type = "async-callback"
   → 典型:异步任务提交、回调注册
   → "业务正确响应"判定:返回非空 task_id 或 accepted 状态

IF 不确定属于哪类
   THEN 停下问用户,禁止自行推断
```

### 5.5.1 验证流程

```
Step 0: 判定 interface_type(见 5.5.0)
   → 填入 stage5.json validation.interface_type

Step 1: 准备测试数据
   → 从 HAR 中提取真实加密参数(作为期望值)
   → 提取对应的输入参数(用户操作/服务端返回/固定常量)

Step 2: 调用方案 1 或方案 2 的产出
   → 方案 1:Python 函数调用,传入输入参数
   → 方案 2:iv8 运行时调用,传入输入参数

Step 3: 比对输出(区分确定性/非确定性,见 5.5.3)
   → 确定性参数(同输入同输出,如加密签名):=== 严格比对(值 + 长度)
   → 非确定性参数(含运行时时序/序列化,如 collect):
      ├─ 结构对齐检查(见 5.5.3)
      └─ httpx 发包按 interface_type 判定(见 5.5.0)
```

### 5.5.2 验证判定

```
IF 确定性参数 === 比对通过
   AND 非确定性参数结构对齐(按 5.5.3 判定)
   AND httpx 发包结果符合 interface_type 的"业务正确响应"标准(见 5.5.0)
   → 验证通过,进入产物整理流程(见 [SKILL.md](../../SKILL.md) "任务完成前产物整理")

IF 任一不通过
   → 回溯:
      ├─ 方案 1:检查算法实现(是否漏步骤/编码错),修正后重试
      ├─ 方案 2:检查补环境是否完整(iv8 debug 报错),补齐后重试
      └─ 若回溯 3 次仍失败 → 触发阶段门阻断,检查阶段二/三是否有遗漏
```

### 5.5.3 非确定性输出结构对齐细则(v9.31 新增,强制)

> 规则来源:JSVMP 字节码产物(如 collect)每次执行内容不同,原"长度匹配"规则无操作化定义,Agent 无法判定 748 vs 1688 是否通过。

```
IF 参数是确定性输出(算法确定,同输入同输出)
   → === 严格比对(值 + 长度必须完全一致)
   → 不一致 = 失败,无例外

IF 参数是非确定性输出(含运行时时序/序列化/随机因子)
   → 结构对齐判定(全部满足才判对齐):
      1. 字段集一致(拆解后字段名齐全)
      2. 值类型一致(字符串/数字/URL编码等)
      3. 编码方式一致(如都是 URL 编码字符串)
      4. 长度在同一数量级(允许 ±50% 浮动,因序列化时序差异)
   → 长度差异 > 50%:
      必须有独立佐证支持"结构对齐即通过"
      佐证 = 同任务至少 1 个确定性参数 === 严格对齐通过
      佐证缺失 → 判失败
   → 长度差异 > 2 倍:
      禁止判通过,无论是否有佐证
      → 必须回溯检查还原是否正确

IF 不确定参数是确定性还是非确定性
   THEN 按确定性处理(=== 严格比对)
   → 不确定性归入更严格分支
```

### 5.5.4 混合实现验证规则(v9.31 新增,强制)

> 规则来源:stage3 §7 允许混合方案(如 JSVMP 走 iv8 + Worker 算子走 Python),但原 §5.5 只描述单一方案验证。

```
IF 实现是混合方案(iv8 + Python,依据 stage3 §7 多特征叠加)
   THEN 各部分独立验证,通过标准 = 全部通过(非加权平均):
      1. iv8 部分:按 5.5.1/5.5.2 验证其产出的参数
      2. Python 部分:按 5.5.1/5.5.2 验证其产出的参数
      3. 混合后的最终输出(如 collect + pow_answer 组合):按 5.5.0 interface_type 发包验证
   → 任一部分失败 → 整体判失败
   → 在 stage5.json validation.samples 中分别记录各部分的验证结果(kind 字段用 "capture-iv8" / "capture-python" / "capture-mixed")
```

## §7 GATE

**检查项**:
- stage5-verify.md 已写入,强制字段齐全
- 分支选择 + 方案选择(分支 C)+ 选择依据已记录
- 加密参数生成方法(Python 函数 API 或 iv8 调用入口)已记录
- 参数溯源表已填写(方案 1 + 方案 2 共同必填)
- 验证结果已记录(固定值 === / 非固定值结构 + httpx 发包)
- 降级原因已记录(若适用)

**通过动作**:
```
运行 `uv run scripts/stage_gate.py --stage 5 --task-dir <path>`
 退出码 0 + status PASS → 进入产物整理流程(见 [SKILL.md](../../SKILL.md) "任务完成前产物整理")
```

**不通过动作**:
- 退出码 1 + status BLOCK → 按 JSON.action 指示回到 §5 流程对应 Step 补齐
- 常见回溯路径:
  - 方案 1 验证不通过 → 检查算法实现(是否漏步骤/编码错),修正后重试(见 5.5.2)
  - 方案 2 验证不通过 → 检查补环境是否完整(iv8 debug 报错),补齐后重试(见 5.5.2)
  - 回溯 3 次仍失败 → 触发阶段门阻断,检查阶段二/三是否有遗漏
- 补齐后重新运行 stage_gate.py

**降级动作**:
- 方案 1 试跑失败 → 快速检查参数对齐排除笔误,非笔误直接降级方案 2(见 5.3.3)
- 方案 1 重写遇不可理解复杂逻辑 → 降级方案 2(见 5.3.2)
- iv8 连续 3 次同类错误 → 止损,回溯阶段二检查脱壳代码完整性(见 5.4.2)
- iv8 调试循环超过 5 轮仍未跑通 → 触发阶段门阻断,检查阶段二/三
- 无法补齐 → 走 [SKILL.md](../../SKILL.md) "任务失败交付物"流程(Black-box reuse 模式已禁用)
